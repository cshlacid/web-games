# 슬리더링크

저장소 전체에 걸리는 규칙은 루트 `CLAUDE.md`에 있다. 여기에는 이 게임에만
해당하는 것만 적는다.

닛코리의 슬리더링크다. 점 사이에 선을 그어 고리 하나를 만들고, 칸의 숫자는 그 칸의
네 변 중 선이 지나는 변의 수다.

## 명령

```bash
node games/slitherlink/rules.test.js      # 변·점·칸 이웃 표, 고리 판정
node games/slitherlink/solver.test.js     # 규칙별 추론, 힌트만으로 끝까지 가는지
node games/slitherlink/generator.test.js  # 구워 둔 판 180장을 다시 푼다(몇 초)

node games/slitherlink/bake.js > games/slitherlink/puzzles.js   # 다시 굽기(3~4분)
```

## 판은 미리 굽는다

쉬움 5×5, 보통 7×7, 어려움 10×10을 예순 장씩 `puzzles.js`에 둔다. 10×10 한 판에 수 초가
걸려 폰에서 "새 판"마다 기다리게 할 수 없다(저장소 규칙의 그 경우다).

**정답 고리부터 만들고 숫자를 지운다.** 칸을 한 칸씩 키워 덩어리를 만들면 그 둘레가
고리다. 둘레가 고리 하나가 되려면 덩어리에 **구멍이 없고**(바깥 칸이 모두 판 가장자리와
이어져 있고) **대각선으로만 맞닿은 자리가 없어야** 한다 — 그런 점에서는 선 넷이 모인다.
모든 칸에 숫자를 적은 뒤, 무작위 순서로 하나씩 지워 보고 풀이기가 여전히 끝까지 풀면
지운 채로 둔다. 이웃이 하나뿐인 칸을 더 자주 골라 가지를 뻗게 한다 — 고르게 고르면
둥근 덩어리가 되어 고리가 단조롭다.

**답의 수를 따로 세지 않는다.** 풀이기는 참인 것만 이끌어 내므로 끝까지 가면 답이
하나뿐이다. 그래서 **추론 규칙은 반드시 옳아야 한다.** "판의 선을 다 품은 덩어리를
닫으면 숫자가 다 맞으니 그 변은 선"은 쓰지 않는다 — 답이 여럿인 판에서 하나를 골라 놓고
풀렸다고 믿게 된다. 마지막 한 변은 점 규칙이 잇는다.

숫자를 다 둔 채로도 규칙만으로는 안 풀리는 고리가 있다(5×5 스무 판 중 둘). 그런 판은
숫자를 하나도 못 지워 칸이 숫자로 뒤덮이므로, 숫자가 60%를 넘게 남은 판은 버린다.

**난이도는 크기와 규칙으로 가른다.** 쉬움과 보통은 칸·점·고리 규칙만으로 풀리는 판이고,
어려움은 "한 변을 선이라 두고 규칙을 돌려 모순이 나면 X"라는 가정을 한 겹 허락하고,
가정이 한 번도 들지 않은 판은 버린다. 3-3이 나란히 붙은 자리, 모서리의 3 같은 정석은
따로 규칙으로 두지 않았다 — 가정 한 겹이 그것들을 다 덮는다.

## 힌트

어긋난 선(정답이 아닌 선, 정답 선 위의 X)을 먼저 걷고, `solver.next`로 **지금 판에서
사람이 다음으로 알아낼 수 있는 변 하나**를 채운다. 규칙을 칸 → 점 → 고리 → 가정 순서로
보므로 쉬운 까닭이 먼저 나온다. 까닭은 풀이기가 `why.code`로 돌려주고 화면이 사전의
`slitherlink.why.*`로 문장을 엮는다.

규칙은 아는 것이 늘수록 더 많이 이끌어 낼 뿐 줄지 않는다. 그래서 틀린 것을 걷어 낸 판은
처음 판보다 아는 것이 많거나 같고, 처음 판을 끝까지 푼 규칙이 거기서도 막히지 않는다 —
힌트가 "알아낼 것이 없다"에 빠지지 않는 이유다.

## 화면

**누르면 가장 가까운 변 하나**가 선 → X → 빈칸으로 돈다. 가로변은 위아래 거리, 세로변은
좌우 거리로 재므로 칸 한가운데는 네 변이 같은 거리라 아무것도 고르지 않는다. 마우스
오른쪽 단추는 X를 바로 찍는다.

**끌면 점에서 점으로 선이 이어진다.** 점에 충분히 다가가야(0.38칸) 닿은 것으로 쳐서,
모서리를 스칠 때 엉뚱한 변이 그어지지 않는다. 손가락이 빨라 점을 건너뛰어도 같은 줄이면
사이의 변을 다 긋는다. 처음 지난 변이 선이었으면 지우는 끌기다.

판에 `touch-action: none`을 걸었으므로 그 안에는 click으로 도는 조작이 없다.

**SVG 좌표에서 칸 한 변은 100이다**(`main.js`의 `U`). 칸을 1로 두었더니 숫자의 글꼴
크기가 0.6이 되어, 폰에서 숫자가 칸 가운데서 비껴 났다 — 웹킷은 이렇게 작은 글자를
viewBox로 키워 그릴 때 글자 폭과 기준선을 작은 크기에서 잰다. 크로뮴은 그대로 가운데라
헤드리스로는 보이지 않는다. 같은 이유로 세로 가운데도 `dominant-baseline`에 맡기지 않고
기준선에서 `dy="0.35em"` 내려 맞춘다(숫자 높이가 글꼴마다 0.7em 안팎이다).

헤드리스에서 빠르게 끈 바로 다음의 첫 두드림은 click이 나지 않는다 — 크로뮴이 관성
스크롤을 멈추는 두드림으로 먹는다. 천천히 떼면 그렇지 않다. 게임의 문제가 아니다.
